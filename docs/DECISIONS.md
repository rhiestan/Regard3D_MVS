# Design and IP decision log

Every design decision with IP, licensing or architectural impact is recorded here with its date, so that
the origin of each technique can be traced later. Algorithms are implemented clean-room from the
published papers listed in the project plan (§1, kept outside this repository); no code is copied from patented or copyleft implementations.

*Not legal advice. Items marked OPEN must be checked against actual patent claims before the related
code is released.*

## Decisions

| # | Date | Decision | Rationale / source |
|---|---|---|---|
| D1 | 2026-10-24 | Primary matcher: pairwise rectified hierarchical Census-SGM followed by multi-stereo triangulation. Reference-view plane sweep is the secondary/fallback matcher. | Hirschmüller, TPAMI 2008 §2.4 (cost-level multi-view fusion is unstable under occlusion); Wenzel et al., ISPRS 2012 (SURE architecture); Hirschmüller & Scharstein, TPAMI 2009 (Census most robust). |
| D2 | 2026-10-24, rev. 2026-10-25 | OpenMVG scenes are read by our own parsers, with no link dependency on OpenMVG or cereal: `sfm_data.json` (nlohmann/json, landmarks streamed through a parser callback) and `sfm_data.bin` (own decoder of cereal's portable binary archive). Versions 0.1-0.3, `view_priors`, all perspective camera models; spherical cameras are read and their views skipped. | Light dependency footprint; decided by the project owner. `.bin` added on 2026-10-25 (owner's request): it is what Regard3D writes, and the JSON is about 10x larger and 70x slower to parse (Luzern: 52 MB / 0.08 s vs. 533 MB / 6 s). |
| D3 | 2026-10-24 | No built-in mesher. Output is a dense point cloud with normals, scale, confidence and optional visibility, for PoissonRecon / FSSR / texrecon. Revisit only if the Phase 7 benchmark shows meshing is the bottleneck. Re-evaluated 2026-10-28 and kept (D43). | Decided by the project owner; see the project plan §3.9. |
| D4 | 2026-10-24 | Third-party code is fetched with CMake FetchContent, pinned to exact releases and verified by SHA256; `R3D_USE_SYSTEM_DEPS=ON` prefers installed packages. Header-only libraries are wrapped without running their CMake scripts. | Reproducible builds without requiring vcpkg/Conan; works identically on all CI platforms. |
| D5 | 2026-10-24 | Own thread pool (`r3d::ThreadPool`) instead of oneTBB for now. Chunk boundaries depend only on the range and grain, never on the thread count, and nested `parallel_for` runs serially. | Deterministic results, no extra binary dependency. Revisit (oneTBB, Apache-2.0) if load balancing of nested/irregular work becomes a bottleneck. |
| D6 | 2026-10-24 | Image decoding via stb_image (JPEG, PNG 8/16-bit, PNM, BMP, TGA); own PNG encoder (8/16-bit, adaptive filters) on stb's zlib compressor. | Zero native dependencies. Revisit in Phase 1 if JPEG decoding speed matters (libjpeg-turbo) or TIFF input is required (libtiff). |
| D7 | 2026-10-24 | C++20 with `std::format`. Minimum compilers: MSVC 19.30, GCC 13, Clang 17, AppleClang 15 (macOS deployment target 13.3). | `std::format` removes the need for fmt; these are the "recent compilers" targeted in the plan. |
| D8 | 2026-10-24 | Point positions are stored as float relative to a double-precision `origin`. PLY output writes either relative float coordinates plus an `r3d_origin` comment, or absolute doubles. | Halves memory for 100M+ point clouds while keeping sub-mm precision for georeferenced scenes. |
| D9 | 2026-10-24 | Eigen is compiled with `EIGEN_MPL2_ONLY`. | Rules out the few LGPL-licensed Eigen code paths at compile time. |
| D10 | 2026-10-24 | Pixel convention: integer pixel coordinates are pixel centres; (0, 0) is the centre of the top-left pixel (OpenMVG convention). The COLMAP importer will shift by −0.5. | Single convention throughout the code base. |
| D11 | 2026-10-24 | Highway kernels must be bit-exact with their scalar reference; tests run every compiled and supported target (`ScopedSimdTarget`). | Deterministic output across machines, and SIMD bugs are caught on every CI platform. |
| D12 | 2026-10-25 | Unit tests use doctest (single header, MIT) instead of Catch2. Own `main` routes MSVC CRT assertion reports to stderr; every CTest test has a 300 s timeout. | Decided by the project owner. Fast to compile, thread-safe assertions; the CRT change fixes a Debug run that blocked on an assertion dialog. |
| D13 | 2026-10-25 | Camera models follow OpenMVG's formulas exactly (`add_disto`), verified against values generated with OpenMVG. The inverse uses damped Newton iteration (accurate to ~1e-12) instead of OpenMVG's bisection / fixed-point iterations. COLMAP models are mapped onto the same models. | One distortion implementation for both importers; OpenMVG's fisheye inverse stops after 10 iterations and is visibly inexact near the border. |
| D14 | 2026-10-25 | Undistortion keeps the focal length and by default covers the whole source image (`keep_all`, invalid corners masked; growth per side capped at 1.5x); `inner` and `same_size` are options. Resampling is bicubic (Catmull-Rom); the distortion is evaluated per output pixel instead of storing maps. A folding distortion (non-positive Jacobian inside the image) is detected and reported. | No source pixel is lost for matching; constant resolution at the image centre. Maps would cost 8 bytes per pixel and camera. Measured: features land within 0.01 px of their pinhole positions. |
| D15 | 2026-10-25 | Pyramids: binomial [1 4 6 4 1]/16 filter, then every second pixel, so pixel i of level k+1 is centred on pixel 2i of level k and the level-k camera is K / 2^k (no half-pixel offset). Integer images are rounded exactly. | Simplest exact geometry for coarse-to-fine matching. |
| D16 | 2026-10-25 | View selection per base view from the SfM tracks: per shared point the weight max_a Gauss(angle; a in {10, 20} deg, sigma 10 deg), zero outside [3, 45] deg, times Goesele's scale weight; pair score = weight sum / points of the base view x coverage (8x8 grid). Greedy choice of up to 4 partners with a penalty for similar baseline directions in the base image. Pairs with a GSD ratio above 2 are rejected; forward motion (epipole in the image) is flagged for the rectification stage. | Goesele et al. 2007 and Wenzel et al. 2014; O(1) memory per view pair. |
| D17 | 2026-10-25 | Optional integration tests run on real scenes from `R3D_TESTDATA_DIR` (default `../testdata`, outside the repository); they are compiled only if the directory exists, so CI runs the synthetic tests only. | Copyrighted / large test images stay out of the repository. |
| D18 | 2026-10-25 | Rectification: calibrated, own implementation of Fusiello, Trucco & Verri (2000) with the mean of both optical axes as viewing direction. The base view is always the left image, at its own focal length. Both images are resampled once from the original (distorted) images; a pyramid level is used as anti-aliasing when the partner is reduced by more than 1.5x. Each rectified image is cropped to 1.5x its source half-size around its rectified principal point, and a pair is rejected only if less than 40% of either image remains (near-forward motion). The disparity range comes from the SfM depth range evaluated on rays across the base image; label counts are multiples of 16. | Single resampling keeps sub-pixel accuracy. Cropping instead of rejecting keeps the near-forward pairs that are common in walk-around captures (6 of 27 best partners in luzern_loewe); the discarded periphery near the epipole has almost no parallax. Polar rectification remains an option for pairs with the epipole inside the image. |
| D19 | 2026-10-25 | Matching cost and penalties: Census 9x7 (62 bits, bit set when the neighbour is darker), Hamming distance 0..62. P1 = 28, P2 = 200, intensity-adaptive P2' = max(P1 + 1, P2 * 4 / (4 + abs(dI))) with dI in 8-bit units. Correspondences outside the right image cost 31; masked left pixels cost 0 for all labels. | Tuned on the Middlebury 2014 training set (H and Q). Census is the most robust cost under radiometric differences (Hirschmüller & Scharstein, TPAMI 2009). |
| D20 | 2026-10-25 | SGM aggregation: 8 paths in two passes (4 paths each, fused in one row kernel), 16-bit saturating arithmetic, path buffers with sentinel labels. Matching costs are recomputed per row in both passes instead of being stored, so only the aggregated volume (2 bytes per label) is kept. Label loops use whole vectors only (full width plus a 16-lane tail), so every SIMD target is bit-exact with the scalar kernels and with a separate textbook implementation used in the tests. | Memory is the limiting resource of full-range SGM (plan section 7); the cost recomputation takes about 30% of the aggregation time. |
| D21 | 2026-10-25 | Disparity selection: winner-takes-all (first minimum), left-right check (tolerance 1 label) against the right image's WTA along the diagonal of the same volume, restricted to valid left pixels; optionally (`lr_full_match`) against a separate right-to-left match on mirrored images (about 1.75x slower, slightly better; the default since D25). Sub-pixel by the equiangular fit (Shimizu & Okutomi 2001), uniqueness test off by default, speckle filter (segments under 100 pixels, step 1) and a 3x3 median of the valid values. | TPAMI 2008 section 2.4. Including masked pixels in the right-image WTA invalidated whole tiles next to masked areas (found on luzern_loewe, regression test added). |
| D22 | 2026-10-25 | Tiling: independent tiles (core 512 px, discarded margin 32 px, linear blending over 32 px), as in TPAMI 2008 section 2.6, with no path costs passed between tiles. The tile layout depends only on the image size and the options (the tile size is halved until a tile fits the memory budget); the number of tiles processed at once is limited by the budget. Results are identical for every thread count. | D5 determinism. Within one pair the parallelism is limited to the tile count; the MVS pipeline (Phase 4) runs pairs in parallel. |
| D23 | 2026-10-25 | Stereo evaluation follows MiddEval3: errors in full-resolution pixels (x4 at Q, x2 at H), the official scene weights, non-occluded mask, holes filled by the SDK's background interpolation for dense scores. The reference SGM is scored by running the same evaluation on Hirschmüller's published MiddEval3 outputs. | Comparable numbers without the SDK. Middlebury's own table uses its upsampling to full resolution, so its numbers differ slightly from ours for the same output. |
| D24 | 2026-10-26 | Hierarchical matching with per-pixel label ranges (tSGM, Rothermel et al. 2012). The coarsest pyramid level (automatic: halve while the next level is at least 96 px and the level has more than 48 labels) is matched over the full range; each finer level searches, per pixel, the min / max of the coarser disparities within a 7x7 coarse window (`range_radius` 3) times two, plus 4 labels on each side (`range_margin`), rounded up to multiples of 16 labels. Each 2x2 block of fine pixels shares one range. Coarse pixels without a disparity take the range of the nearest valid ones (min / max pyramid, up to about 64 coarse pixels, `range_fill`), beyond that the full range. Ranges are clipped to labels whose match lies inside the partner image's valid columns. A minimum on the edge of a reduced range is rejected. Every level is post-filtered (LR check, speckle filter scaled by 4^-level, median). The SGM recursion treats labels outside a predecessor's range as infinite (exact textbook semantics, bit-exact on every SIMD target). Labels stay uniform in disparity; there is no cost compression. | Middlebury 2014 H with the full LR check: 80.1% density / 8.6% bad-2 against 77.9% / 9.1% for Phase 2 full range, at 67 instead of 219 cells per pixel; Q on par. Radius 3 and margin 4 were the best of 1-3 / 2-8 (wider margins admit more ambiguous matches). Shared 2x2 ranges cut the predecessor re-alignments and made aggregation about 40% faster. Real scenes: 1.5-40x faster than full range, with equal or higher density. |
| D25 | 2026-10-26 | The left-right check against a full right-to-left match is the default (`lr_full_match`; `--lr-diagonal` selects the check along the diagonal of the same volume). The right-to-left match runs on the mirrored pair with its own per-pixel ranges from the coarser right disparities; both maps are checked against each other and filtered at every coarser level. | With reduced ranges the diagonal check sees fewer competing labels and accepts more errors (H: 10.4% against 8.6% bad-2). The full match costs about 2x, which the hierarchy more than recovers. Fixed with it: the mirrored pair's disparity offset was wrong (wl - wr instead of wr - wl) for rectified images of different widths, which made the Phase 2 option unusable on real pairs (regression test added). |
| D26 | 2026-10-26 | Memory: Census values are computed per tile (on the tile and the right columns its labels reach, enlarged by the window radius, so they equal the whole-image values); tiles are admitted by a byte-counting gate against `memory_budget` instead of a fixed number of slots, since their sizes now differ. Per-pixel data: 16-bit range starts, no confidence for the right-to-left match, mirrored ranges built directly. | A 24.7 MP pair (2528 labels) peaks at 1.2 GB with a 256 MB budget and 1.9 GB with the default 2 GB budget (about 40 bytes per pixel plus the tiles in flight). |
| D27 | 2026-10-27 | Multi-stereo triangulation per base view (Phase 4): the base view is matched with its up to 4 best partners (D16), always as the left image, and all pairs are combined on one depth grid (the undistorted camera scaled by `--resolution`). In each rectified pair the disparity is linear in the base view's inverse depth w (d = k w + offset, k = f b / c), so a pixel's pairs vote in 1-D along the base ray: the hypothesis with the most pairs within 2 px wins (a tie needs two agreeing pairs), w is the k²-weighted mean of the winners (least squares in disparity), pairs with a residual above 1 px are dropped, and the largest triangulation angle must reach 3°. One pair suffices; disparities are sampled bilinearly only inside smooth surfaces. Colour comes from the undistorted image on the same grid. | Exact and cheap (no plane sweep, no reprojection search): every pair's disparity maps straight onto the base ray. Keeping single-pair depths matters for completeness; the consistency stage (D28) removes the unreliable ones. |
| D28 | 2026-10-27 | Geometric consistency: a depth agrees with a neighbouring view when its point meets that view's depth within 1% and reprojects back within 2 px. Neighbours are the view's partners plus the views that chose it as partner (at most 8). Pixels next to relative depth jumps over 5% are removed first. A depth is kept when its agreeing pairs plus agreeing views number at least 2 (`min_evidence`; two pairs, or one pair confirmed by another view); it is then replaced by the mean depth of the agreeing views along its ray. Agreement is computed on the unfiltered maps, then applied. Agreement between the two depth maps of the same image pair counts (`--independent-support` optionally discards it, using the per-pixel pair mask). | ETH3D training, F1 at 2 cm, half resolution, against the alternatives: requiring an independent pair cost 8-18 points of completeness on office / pipes (F1 0.570 / 0.479 vs 0.638 / 0.609); requiring one agreeing view lost 2 points on terrains; keeping every depth raised office F1 to 0.678 but left 9% of its points more than 50 cm off (accuracy at 50 cm 0.906 vs 0.991). Averaging raised courtyard accuracy at 2 cm from 0.757 to 0.804. |
| D29 | 2026-10-27 | Fusion (Phase 4 version): voxel grid with voxel size = median GSD of all depths (`--voxel`, `--voxel-factor`); entries are sorted by a 64-bit key (21 bits per axis) in parallel, and each voxel's points are averaged with weights 1 / GSD². Normals come from the depth maps' 4-neighbours (not across 5% jumps), oriented towards the camera; colours are averaged. The PLY carries `value` (GSD, the point scale for FSSR) and `confidence` (fused pixels). Coordinates are relative to a rounded origin for georeferenced scenes (more than 1e4 units from zero), written in double precision. | Deterministic, O(n log n), a few seconds for 200 M depths; the octree with best-resolution-wins replaces it in Phase 6. |
| D30 | 2026-10-27 | Depth maps are cached per view in the work directory (`depth_<view>.r3dd`, versioned binary: depth, confidence, pair mask, partners, colour); `--reuse` skips matching for cached views, so the consistency and fusion options can be tuned in seconds. | Matching is 95% of the run time. |
| D31 | 2026-10-27 | Benchmark: ETH3D high-res multi-view training scenes, scored with the official `multi-view-evaluation` tool (BSD), built outside the repository without PCL / Boost through a small compatibility header and nanoflann. Reference numbers come from COLMAP 4.2 (CUDA patch-match stereo, default options) at the same resolution (`--max_image_size 3104`). Phase 4 result at half resolution, F1 at 2 cm (COLMAP): courtyard 0.797 (0.766), office 0.639 (0.374), pipes 0.606 (0.376), terrains 0.821 (0.719); 70-200 s per scene on 32 threads against 1060-3840 s for COLMAP on the GPU. Our clouds are more complete; COLMAP's are more accurate (2 cm accuracy 0.89-0.98 vs 0.78-0.89). | Same images, same resolution, same evaluation; COLMAP's leaderboard entries use full resolution. The accuracy gap at 1-2 cm is the target of the Phase 5 refinement. |
| D32 | 2026-10-27 | Refinement (Phase 5), after the multi-stereo depth maps and before the consistency check: every depth is refined as a plane in the base view's inverse depth, w(q) = w + a dx + b dy (affine in pixel coordinates for any plane), by Gauss-Newton on the sum over views of squared differences of normalised windows (2 - 2 NCC per view; gain and offset invariant). Window 9x9 sampled every 2 px, 6 iterations, steps limited to 1 px of image motion and halved when the score drops. Images: grey levels on each view's depth-map grid with central-difference gradients, bilinear sampling; the base window is read at integer pixels. Up to 4 neighbouring views (consistency neighbours); per pixel only views with NCC >= 0.3 at the initial depth take part. A refined depth is taken only when the mean NCC rises by at least 0.02 and it moved by at most 2 px in every used view; the confidence becomes the mean NCC. Deterministic, scalar; no random search. | Synthetic 42° plane from stair-stepped depths with 1% error: relative RMS 0.68% -> 0.07% (9x). On ETH3D, SGM is already precise on frontal surfaces (median depth error 0.06-0.14% against the scan on pipes) and an unconditional refinement made them worse (courtyard view 5, accuracy at 1 cm on surfaces facing the camera 0.987 -> 0.934, a small shift towards the camera that blur, smaller / larger windows and other view sets did not remove), while it helped on oblique surfaces and at depth edges. The 0.02 gain threshold keeps the gains and most of the frontal precision (frontal 0.987 -> 0.984, 50-75° 0.97 / 0.90 -> 0.98 / 0.92). Larger windows (11x11) cost 5x the time for the same F1. SIMD for this stage is deferred: it takes 19-102 s per scene, 15-50% of the matching time. |
| D33 | 2026-10-27 | Erosion at the border of invalid regions (`--erode-holes`) is available but off. | Per view, pixels within 1 px of a depth jump or hole are 15% inaccurate at 2 cm (pipes view 9). Eroding hole borders raised accuracy (courtyard 0.804 -> 0.824 at 2 cm) but lowered completeness by the same amount: F1 courtyard 0.806 / 0.806, pipes 0.615 / 0.596. |
| D34 | 2026-10-27 | Benchmark insight for the filtering work (Phase 6): ETH3D accuracy is the mean over 1 cm voxels of the accurate fraction of the points in each voxel, not the fraction of accurate points. Isolated wrong points each count like a whole voxel of correct surface. Pipes: the depth maps are 70-99% accurate per point (about 94% overall), the fused cloud scores 0.78. Errors concentrate at depth edges / hole borders and in single-pair depths (9.5% inaccurate against 0.2% with two agreeing pairs). | The remaining accuracy gap to COLMAP (2 cm: 0.77-0.88 vs 0.90-0.98) comes from scattered points, not from depth precision, so it is addressed by outlier / visibility filtering of the fused cloud (Phase 6), not by more refinement. |
| D35 | 2026-10-28 | Visibility filter after the consistency check (on by default): a depth conflicts with a neighbouring view when it lies in that view's free space, or when the view sees a surface in front of it along the depth's own ray (the neighbour's depth map rendered into the view, nearest depth per pixel). A conflict needs a 2% depth margin over the whole 3x3 neighbourhood (robust to depth edges misaligned by a pixel); a depth is removed when at least 2 of the 8 neighbours conflict and more neighbours conflict than agree. | Terrains (reflections on the floor, the ceiling's metal cable guide, a display behind glass): 1.4% of the depths that can be checked against the scan lie more than 2 cm behind it, a quarter of them more than 58% behind (reflections). The filter removes only 3% of them, with 8 or 20 neighbours: 90% of these depths have no conflicting neighbour, because the neighbours have no depth on the reflecting floor there or see the same (geometrically consistent) mirror image. It is cheap (1-9 s per scene) and gains a little accuracy (terrains F1 at 2 cm 0.818 -> 0.820). ETH3D ignores points behind the scanned surfaces, so the benchmark does not measure reflection points; they were counted against a z-buffer of the scan. |
| D36 | 2026-10-28 | Speckle removal after the consistency check (`--depth-speckle-size`, connected segments with relative depth steps up to 2%) is available but off. | 70% of the gross errors behind surfaces lie in segments under 100 px, 90% under 300 px, against 1-2% of the correct depths. At 100 px it removes 38% of the stray depths on terrains (1.40% -> 0.87%) for F1 at 2 cm 0.820 -> 0.818 (completeness -1.4 points); with fold validation it lowers F1 in every combination (terrains 0.848 -> 0.841, pipes 0.602 -> 0.561). Agreement counts (DepthMap::support) do not separate good small segments from bad ones. |
| D37 | 2026-10-28 | Fusion is a linear octree (plan.md section 3.8): every pixel gets a leaf of `voxel_factor` x its GSD, rounded to a power of two times the finest leaf (1st percentile of the GSD; levels up to the 99.9th percentile). Points are sorted by the Morton code of their finest cell, so every cell at every level is a contiguous range. Best resolution wins: a point is dropped when its leaf holds at least two points with a GSD 2x finer. Space is split into chunks of 64 coarsest leaves per axis, fused independently in batches within `--fusion-memory` (one pass over the depth maps per batch); 40-byte point records. The result does not depend on the number of passes (bit-identical PLY). | ETH3D, F1 at 2 cm against the Phase 5 voxel grid (one voxel size, the median GSD): courtyard 0.806 -> 0.801, office 0.640 -> 0.640, pipes 0.615 -> 0.622, terrains 0.819 -> 0.821. Courtyard prefers the coarse fixed voxel (fine views get 1.2 mm leaves at a 5.4 mm median GSD and are hardly averaged); a leaf factor of 2 cuts the clouds 2.5-4x and gains on pipes / terrains (0.635 / 0.828) but loses on courtyard (0.789), so the default stays 1 and `--voxel-factor 2` is the density option. Best resolution wins drops 1-3% of the points; ETH3D's views have similar GSDs where they overlap, so it has no measurable effect there. |
| D38 | 2026-10-28 | Fold validation (`--min-sources`, distinct views per fused point, counted in the leaf) is available, default 1. Counting the 26 neighbouring leaves as well (`--fold-neighbourhood`) is off. | F1 at 2 cm with 2 sources: courtyard 0.801 -> 0.804, office 0.640 -> 0.608, pipes 0.622 -> 0.602, terrains 0.821 -> 0.848 (accuracy 0.83 -> 0.92, 93 M -> 41 M points). It removes the scattered single-view points that dominate ETH3D's voxel-averaged accuracy (D34), but scenes with few views (pipes 14, office 26) lose more completeness than they gain. 3 sources is much worse (terrains 0.805, pipes 0.389). The neighbourhood variant keeps more points but is worse than the leaf on three scenes (courtyard 0.792, office 0.613, pipes 0.604, terrains 0.829). |
| D39 | 2026-10-28 | The dense pipeline keeps depth maps in per-stage stores within `--memory` (default 8 GB): maps that do not fit are written to the work directory (or a temporary directory) and read again when needed; refinement images are cached the same way. Each stage loads one view and its neighbours. Raw and refined maps are cached in the work directory (`--reuse`, `--reuse-refined`). The consistency check is split into a per-view preparation (confidence, edge erosion) and a per-view check against the prepared neighbours, the visibility filter likewise, so the results do not depend on the processing order. | Phase 5 held all depth maps (14 bytes per pixel) and grey images at once: about 3 GB for ETH3D terrains at half resolution, about 45 GB for 500 views of 6 MP. Courtyard with `--memory 1024 --fusion-memory 256`: identical cloud, 21 fusion passes, peak memory 9.3 GB -> 5.2 GB. The rest is the output cloud (67 M points), which is held in memory until the PLY is written; streaming it is left for the export work (Phase 7). |
| D40 | 2026-10-28 | Export for external tools (plan.md section 3.9): `r3dmvs export` and `dense --for` write one of three point layouts. `full`: everything (positions, normals, colours, `value` = point footprint, `confidence` = fused depths, optional `view_ids` with `--with-views`). `poisson`: positions, normals, colours, with the normals scaled to min(1, fused depths / 4) for `PoissonRecon --confidence`. `fssr`: `value` = 8 x footprint as the sample scale, `confidence` = min(1, fused depths / 4). The texrecon scene (`export --texrecon-dir`) is a folder with one JPEG and one `.cam` per view: undistorted with the same K and size (images without distortion are copied), focal length / larger side, aspect fy / fx, principal point (c + 0.5) / size (MVE pixels span [i, i + 1), ours are centred on i). | Lets every free mesher use what the cloud knows without its own estimation (normals from the depth maps, scale from the GSD). The `.cam` convention was checked against MVE's projection (unit test) and on ETH3D office, whose texture atlases line up with the geometry. The confidence weights and the FSSR scale come from the mesh benchmark (D42). |
| D41 | 2026-10-28 | The dense cloud is written while it is fused: the fusion hands each batch of chunks to a sink, which converts it to the requested layout and appends it to the PLY (`PlyWriter`; the vertex count is written on close into a header field padded with spaces). | Removes the last whole-cloud buffer (D39). Courtyard with `--memory 1024 --fusion-memory 256`: peak memory 5.2 GB -> 1.1 GB, bit-identical points. PoissonRecon, fssrecon, texrecon, the ETH3D evaluation and our reader accept the padded count. |
| D42 | 2026-10-28 | Meshing recipe (`tools/r3d_mesh.py`): mesh a cloud fused with `--voxel-factor 2`. Poisson: octree depth with cells of about 6x the median footprint in PoissonRecon's bounding cube (at most 12), confidence-weighted normals (`--confidence`), SurfaceTrimmer at 10. FSSR: sample scale 8x the footprint, meshclean with threshold 1 and components of at least 10000 vertices. Faces of zero area are removed before texrecon. | ETH3D (half resolution), mesh sampled at 2 mm (courtyard 5 mm), F1 at 2 cm. The full-density cloud meshes no better than the voxel-factor-2 cloud (pipes 0.568 vs 0.563 at depth 12) at several times the cost. Depth: pipes 11 / 12 0.573 / 0.563, office 9 / 10 / 11 0.605 / 0.619 / 0.616, terrains 12 / 13 0.809 / 0.809 (14 M vs 51 M faces); depths above 12 only make texrecon slow (office at depth 12, 45 M faces: 96 min, then a crash). Trim 8 / 10 / 12 on pipes 0.575 / 0.568 / 0.439 at depth 12 (trim 8 keeps hallucinated surface, 250 vs 120 m2) and 0.568 / 0.573 at depth 11. Confidence weights: office 0.619 -> 0.629, courtyard 0.765 -> 0.780, pipes 0.573 -> 0.571, terrains 0.801 -> 0.809. FSSR scale 2 / 4 / 8 on pipes: 0.500 / 0.532 / 0.541, 86 / 15 / 5 min; a meshclean threshold of 3 or 8 is worse (0.534, 0.509). texrecon (2017 build shipped with Regard3D) aborts in "Generating texture patches" on zero-area faces (zero-length face normals; found by bisecting a crashing pipes mesh down to 3442 faces with 4 such faces); meshclean does not remove them. A second crash remains (access violation, same step) on the terrains Poisson mesh, reduced to a connected piece of 1695 faces that textures fine when split; skipping hole filling does not help, the cause is open, and FSSR meshes have not triggered it. PoissonRecon's thread pool spins without progress when the machine is oversubscribed. |
| D43 | 2026-10-28 | D3 re-evaluated: no built-in mesher. ## Avoided techniques (from the earlier design review, `input.txt`)

| Technique | Status |
|---|---|
| eSGM-style storage of per-direction minima only | Avoided: the full aggregated cost volume of each tile is stored. |
| Cost compression / disparity sub-sampling of path costs | Avoided: full label resolution, `uint16` aggregated costs. |
| Tiling that passes boundary path costs between tiles | Avoided: independent overlapping tiles with blending (TPAMI 2008 §2.6). |
| Non-uniform disparity labels | Avoided: uniform disparity (rectified) or uniform inverse depth (plane sweep). |
| PatchMatch randomised search (as in COLMAP/OpenMVS) | Avoided as the core; refinement uses deterministic least squares (Goesele et al. 2007, MPGC). |
